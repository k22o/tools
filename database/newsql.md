# NewSQL

## 概要

RDBの考え方とNoSQLの持つスケーラビリティなどの優位性を組み合わせたDBのこと。
※ RDBにもスケールアウトなどの考え方はあったので、完全に背反する概念ではないことに注意。

プロダクト例

- Google Cloud Spanner
- Amazon Aurora DSQL
- TiDB
- YugabyteDB
- CockroachDB

## NewSQLの技術要素

### ストレージエンジン

- NewSQLでは、クエリエンジンとストレージエンジンが分離されており、それぞれが独立にスケールアウトできるようになっている (ことが多い...？）
- ストレージエンジンでは、RDBで一般的なB-Treeではなく、より高い書き込み性能を実現できる、LSM-Treeが利用されることが多い
　 - 読み取り性能はB-Treeの方が良いので、それを補う工夫を別途している 

### シャーディング

- RDBとは基本的に同じ概念

### Raft（分散合意アルゴリズム）

分散システムにおいて複数ノード間のデータの一貫性を保つための分散合意アルゴリズム（Consensus Algorithm）。

- 複数ノード間でデータの更新内容に合意する。
- ログを複製し、各ノードの状態を一致させる。
- 一部のノードが故障しても、過半数が稼働していれば処理を継続できる。

#### ノードの役割

| 役割 | 説明 |
|---|---|
| Leader | 書き込み要求を受け付け、ログの複製を管理する |
| Follower | Leaderからログを受け取り、複製する |
| Candidate | Leader選出のために投票を求める |

通常時は1つのLeaderと複数のFollowerで構成される。

#### 処理の流れ

1. クライアントがLeaderに書き込み要求を送信する。
2. Leaderがログに追加し、Followerに送信する（AppendEntries）。
3. Followerがログを保存し、Leaderに応答する。
4. 過半数のノードへの複製が完了するとCommitされる。
5. 各ノードがCommitされたログを順番に適用する。
6. Leaderがクライアントに結果を返す。

※厳密には、現在のTermのログエントリについて過半数への複製を基準にCommitする。
