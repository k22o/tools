# メッセージング

ソフトウェアにおける「メッセージング」とは、コンポーネントやサービス同士がネットワークを介してメッセージ（データやイベントの塊）をやり取りする仕組みのこと。REST APIのような同期的な呼び出しと対比され、送信側と受信側が疎結合になる点が特徴。

- **同期通信**: リクエストを送ったら応答が返るまで待つ方式（例: HTTP/REST, gRPC）。呼び出し元と呼び出し先が処理タイミングを共有するため結合度が高い。
- **非同期通信**: メッセージを送った後、応答を待たずに処理を続ける方式。送信側と受信側の可用性・処理速度が切り離される。

## 動機通信

### REST

HTTP上でリソースをURLで表現し、GET/POST/PUT/DELETEなどのHTTPメソッドで操作するアーキテクチャスタイル。Web APIのデファクトスタンダードとして広く使われる。

- 特性
   - **リソース中心設計**: URL がリソースを表し、HTTP メソッド（GET / POST / PUT / DELETE）で操作を表現する
   - **ステートレス**: サーバーはリクエスト間の状態を保持しない
   - **キャッシュ可能**: HTTP のキャッシュ機構をそのまま利用できる
   - **統一インターフェース**: 標準的な HTTP 規約に従うため、汎用クライアントで利用しやすい
   - **テキストベース**: JSON / XML でやり取りするため人間が読みやすい
- 課題
   - **Over-fetching**: 必要以上のデータが返ってくる
   - **Under-fetching**: 1 回のリクエストで必要な情報が揃わず、複数回リクエストが必要になる（N+1 問題）
   - **バージョン管理**: エンドポイントの変更に `/v1` `/v2` などのバージョニングが必要になりがち



### gRPC

Googleが開発した、Protocol Buffersをシリアライズ形式に使うRPC（Remote Procedure Call）フレームワーク。HTTP/2上で動作する。

- 特性
   - **強い型付け**: `.proto` ファイルでスキーマを定義し、コードを自動生成する
   - **バイナリ転送**: protobuf によるシリアライズで JSON より高速・軽量
   - **ストリーミング対応**: ストリーミング（単方向・双方向）、多重化、ヘッダー圧縮が使える 
   - **多言語対応**: protobuf から各言語のスタブを自動生成できる
- 課題
   - ブラウザからの直接呼び出しが難しい（gRPC-Web が必要）
   - バイナリ形式のためデバッグしにくい
   - HTTP/1.1 ロードバランサーとの相性が悪いケースがある
   - REST に比べてエコシステムが小さい


### graphQL

クライアントが必要なデータの形をクエリとして指定し、単一のエンドポイントから取得できるクエリ言語。

- 特性
   - **クライアント主導のデータ取得**: 必要なフィールドだけをリクエストできる（Over/Under-fetching を解消）
   - **単一エンドポイント**: `POST /graphql` の 1 エンドポイントにすべてのクエリが集約される
   - **型システム**: SDL（Schema Definition Language）でスキーマを定義し、型安全なクエリを書ける
   - **3 つの操作**:
     - `Query`（読み取り）
     - `Mutation`（書き込み・更新・削除）
     - `Subscription`（リアルタイム購読）
   - **イントロスペクション**: スキーマ自体をクエリで取得でき、自己文書化されている
- 課題
   - **N+1 問題**: リゾルバの実装次第で DB クエリが爆発する（DataLoader パターンで緩和）
   - **キャッシュ**: REST のような HTTP キャッシュが使いにくい（クエリごとにキャッシュキーが異なる）
   - **複雑なクエリ対策**: 深いネストや大量フィールドの悪意あるクエリへの防御が必要
   - **学習コスト**: クエリ言語・リゾルバ設計の習得が必要

## 非同期通信

### pubsub（Publish/Subscribe）

Publisher（発行者）が送ったメッセージを、そのトピックを購読している複数のSubscriber（購読者）全員に配信するモデル。Apache Kafka・Google Pub/Subなどが代表例。
Event-Driven（イベント駆動アーキテクチャ）の設計思想。

- 1つのメッセージを複数の受信者にブロードキャストできる
- PublisherはSubscriberの存在や数を意識しなくてよいため、疎結合性がさらに高まる

**Apache Pulsar**は、pub/sub（ログ保持型のトピック配信）とMQ（キュー型消費）の両方の性質を併せ持つハイブリッドな立ち位置。トピックごとにSubscriptionモードを選べ、`Exclusive`/`Failover`は1コンシューマーが専有、`Shared`/`Key_Shared`は複数コンシューマー間でメッセージを分散する（MQのポイントツーポイントに近い）。Kafkaと異なりブローカーとストレージ（BookKeeper）が分離されたアーキテクチャを持つ。

### MQ（メッセージキュー）

送信側（Producer）がメッセージをキューに送り、受信側（Consumer）が自分のタイミングで取り出して処理する仕組み。RabbitMQ・Amazon SQSなどが代表例。Event-Driven（イベント駆動アーキテクチャ）の設計思想。

- キューがバッファとして機能するため、受信側がダウンしていても送信側は処理を続けられる（可用性の向上）
- 受信側の処理能力に合わせてメッセージを取り出せる（負荷平準化）
- Producerにつて、基本的には1つのメッセージを1つのConsumerが処理する「キュー型（ポイントツーポイント）」のモデルだが、RabbitMQなどの実装ではexchange（fanout/topicタイプなど）を介してメッセージを複数のキューにコピーできるため、pub/subに近い配信も表現できる
- Consumerは、push型（ProducerがConsumerに送りつける）とpull型（Consumerが自分のタイミングで取りに行く）のパターンがある
